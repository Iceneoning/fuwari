# 03：按阶段优化 LCP

## 问题

Lighthouse 将「LCP 细分」标记为待优化项。当前截图没有展开最大内容绘制元素，也没有显示各阶段的耗时，所以暂时不能判断瓶颈来自服务器响应、资源发现、资源下载还是渲染延迟。

## 目标

- 确认每个主要页面的 LCP 元素。
- 找出 LCP 总耗时中占比最高的阶段，实施对应优化。
- 避免为了改善单一页面而损害缓存、图片质量或其他页面体验。

## 取证步骤

1. 在生产构建下分别测试首页、文章页以及截图对应页面。
2. 记录 LCP 元素的选择器、资源 URL、尺寸和是否位于初始 HTML 中。
3. 保存 LCP 各阶段数据：TTFB、资源加载延迟、资源加载时长和元素渲染延迟。
4. 检查 LCP 资源的优先级、懒加载设置、响应式尺寸、压缩格式和缓存策略。
5. 联合「渲染阻塞请求」结果，确认 CSS 是否延迟了 LCP 元素的绘制。

## 按阶段选择方案

| 主要耗时阶段 | 优先排查方向 |
| --- | --- |
| TTFB | 静态输出、CDN 缓存、重定向和服务端响应链路 |
| 资源加载延迟 | 资源是否能从初始 HTML 及时发现、是否被错误懒加载、请求优先级是否合理 |
| 资源加载时长 | 图片尺寸、压缩格式、响应式资源和缓存命中 |
| 元素渲染延迟 | 渲染阻塞 CSS、字体、主线程长任务和进入动画 |

如果 LCP 元素是图片，应先确认实际显示尺寸和资源发现时机，再决定是否预加载。不要预加载所有候选图片，否则可能与真正的首屏关键请求竞争带宽。

## 本轮已实施的 LCP 上游优化

当前内置浏览器没有返回 `largest-contentful-paint` 条目，因此本轮没有足够证据指定具体 LCP 元素，也没有用 DOMContentLoaded 代替 LCP。已实施的调整集中在明确会影响元素渲染延迟的上游路径：

- 友链页渲染阻塞 CSS 从 6 个请求降为 2 个，并显著降低压缩体积。
- 移除所有页面首屏同步执行的 OverlayScrollbars，公共布局脚本 gzip 从约 `15.98 kB` 降到约 `1.67 kB`。
- PhotoSwipe CSS 和逻辑仅在存在可放大图片时按需加载，不参与友链页首屏。
- 鼠标特效空闲时停止动画帧，减少首屏之后无意义的主线程与合成工作。
- 为当前作者头像补充 `400 × 425` 的固有尺寸，避免慢速加载时容器尺寸不确定。
- 保留站点背景图的 `preload` 与 `fetchpriority="high"`；在确认 LCP 元素前不增加更多高优先级预加载，避免资源竞争。
